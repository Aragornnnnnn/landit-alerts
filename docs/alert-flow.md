# 알림 판정 흐름

각 알림이 언제 발송되고 언제 무시되는지 정리한다.
공통 전제는 두 가지다.

- 30분마다 스토어에 현재 상태를 물어보고, 지난 실행에 저장한 상태와 비교한다.
- 첫 실행은 기준점만 저장하고 아무것도 보내지 않는다.

## 새 리뷰

```text
리뷰 목록 수집
→ 저장된 "본 리뷰 ID 목록"에 없는 ID인가?
  ├─ 예 → 알림 발송, ID를 목록에 추가
  └─ 아니오 → 무시
```

ID 기준이라 같은 리뷰가 두 번 알림될 수 없다.
스토어 응답이 흔들려서 옛 목록이 와도, 이미 본 ID는 전부 목록에 있으므로 조용하다.

## 새 버전 공개

```text
스토어에서 버전 수집
→ 저장된 버전보다 높은가? (숫자 단위 비교)
  ├─ 예 → 알림 발송, 버전 저장
  └─ 아니오 (같거나 낮음) → 무시
```

"다르면 알림"이 아니라 "높아야 알림"이다.
배포 직후 스토어 서버들이 옛 버전을 섞어 응답해도, 낮은 버전은 무시되므로 반복 알림이 없다.

## 애플 심사 상태 (ASC 키 등록 후)

```text
최신 버전의 심사 상태 수집
→ 저장된 상태와 다른가?
  ├─ 출시 대기(PENDING_DEVELOPER_RELEASE)로 바뀜 → 심사 통과 알림
  ├─ 거절(REJECTED·METADATA_REJECTED)로 바뀜 → 심사 거절 알림
  └─ 그 외 전이 → 무시 (상태만 저장)
```

## 왜 이런 방어가 필요한가 — 2026-08-09 실사례

1.1.0 릴리즈 당일, 이런 알림이 실제로 반복됐다.

```text
14:24  평점 4 → 4.3 ▲            (정당)
14:24  랜딧 1.1.0 공개됨          (정당)
19:16  평점 4.3 → 4 ▼ · 리뷰 4개  (가짜 — 리뷰 수까지 과거로 후퇴)
19:16  랜딧 1.0.0 공개됨          (가짜 — 옛 버전을 새 공개로 오인)
22:53  평점 4 → 4.3 ▲            (가짜 — 원상복구를 변동으로 오인)
22:53  랜딧 1.1.0 공개됨          (가짜 — 반복)
```

원인은 스토어 API가 단일 서버가 아니라는 것이다.
전 세계 캐시 서버가 값을 나눠 들고 있고, 값이 바뀐 직후엔 서버마다 최신값과 옛값이 섞여 있다.
호출할 때마다 다른 서버가 응답하므로, 실제로는 한 번 변한 값이 여러 번 변한 것처럼 관측된다.

이건 스토어 쪽을 고칠 수 없는 문제라서 받는 쪽에서 거른다.
버전의 "높아야 알림" 규칙이 그 방어다.
평점 변동 알림은 이 사건을 계기로 아예 제거했다.
공식 API가 평점 집계를 제공하지 않아 불안정한 공개 값에 의존해야 했고, 별점만 남긴 평가에 대한 알림은 대응할 것도 없어서 가치가 낮았기 때문이다.
같은 이유로 데이터 소스도 키 등록에 맞춰 공식 인증 API(App Store Connect·Play Developer)로 순차 전환한다.
